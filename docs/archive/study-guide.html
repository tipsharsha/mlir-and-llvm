Overview of the series

1. The story in ten sentences

  1. AI needs a lot of compute, and the demand grows. (Part 1)
  2. Most AI compute runs on NVIDIA GPUs, which developers program with CUDA. (Parts 2 and 3)
  3. CUDA is a whole platform: a language, a driver, libraries and complete solutions. NVIDIA owns all of it. (Part 2)
  4. CUDA won through strategy: one compatible GPU line, strong libraries and good timing with AI. (Part 3)

  9. Modular bets on a new stack, built in closed research and then opened. (Part 10)
  10. The stack has layers: Mojo, MAX and Mammoth. Modular says that one build runs on NVIDIA GPUs, AMD GPUs and CPUs. (Part 11)

20-00-00General

Primer: ten ideas to know before you read

The series uses many GPU and AI terms. This primer explains the ten that appear most. Read it once, then read the digests.

Table 5 · Ten ideas
No.IdeaExplanation
1CPU and GPUA CPU runs a few threads at high speed. A GPU runs thousands of simple threads at the same time. The math of AI fits the GPU.
2KernelA function that runs on the GPU. The GPU runs many copies of it at the same time, each on different data.
3Thread, block, warpA kernel starts a grid of blocks. Each block has threads. On NVIDIA hardware, threads run in groups of 32, which are called warps.
4Memory levelsRegisters are the fastest. Shared memory (SRAM) is on the chip. Global memory (HBM) is large but slow. Data movement often costs more than the math.
5Tensor CoreA special GPU unit that multiplies small matrices at high speed. Most of the FLOPs of an AI model run on Tensor Cores.
6PTXAn assembly-like language for NVIDIA GPUs. CUDA code compiles to PTX. The driver then makes machine code. The LLVM NVPTX back end also makes PTX.
7Library, framework, compilerA library gives ready kernels (cuBLAS). A framework lets you describe models in Python (PyTorch). A compiler makes kernels for you (TVM, XLA).
8Kernel fusionSeveral operations run in one kernel. This saves memory traffic. See Figure 2.
9Training and inferenceTraining changes the weights of a model and takes a long time. Inference uses the trained model to give answers. GenAI serving is mostly inference at large scale.
10IR and dialectAn IR is the form of code between the source and the machine code. LLVM has one IR. MLIR lets you define many IRs, which are called dialects.

READING R1-P1Part 1 · DeepSeek’s impact on AI—

Week 0Chris Lattner · 30 January 2025 · Original article

1. Main idea

DeepSeek showed that new ideas and better use of existing hardware can reduce the need for costly GPUs. Lattner says AI demand will still grow. Thus the cost of AI compute must go down. This part starts the series and gives its questions.

2. Key points

  1. The belief under test: only companies with huge compute can lead in AI. DeepSeek’s results weaken this belief. A small, focused team challenged large companies.
  2. Lattner expects a surge in demand for AI applications. If hardware access and software do not improve, progress stops at hardware shortages or at poor tools.
  3. He names three ways to reduce the total cost of ownership (TCO). They are: wider access to other hardware, more efficiency from current systems and faster software.
  4. He gives his background, because it explains his view. He founded LLVM. At Apple he worked on OpenCL, moved the CPU and GPU software to LLVM, and helped create Swift.
  5. In 2017 he joined Google to lead software for the TPU. The hardware was ready, but the software was not. TPUs worked only in part with PyTorch.
  6. His diagnosis: customers were not able to run any model they wanted on TPUs. The missing piece was CUDA, which is the de facto standard for AI development.
  7. Since then he has worked on MLIR, which many AI compilers now use. His team at Modular worked for about three years on a project that it did not yet show.
  8. Money and motivation are not the cause of the problem. Lattner says the problems are foundational. He tells the reader to look at the roots under product news.

READING R1-P2Part 2 · What exactly is “CUDA”?—

Week 0Chris Lattner · 5 February 2025 · Original article

1. Main idea

CUDA is not one thing. It is a layered platform of a language, a driver, libraries and complete solutions. Lattner proposes the name “the CUDA Platform”. You must know the whole platform before you plan a way out of the lock-in to NVIDIA.

2. Key points

  1. People have partial views. To some, CUDA is a language. To others, it is a framework or “the thing that makes NVIDIA GPUs fast”. None of these views is complete.
  2. The history: early GPUs were fixed-function. Rendering steps were hardwired. In 2001, the GeForce3 added programmable shaders. Then researchers used GPUs for work that is not graphics. The BrookGPU project at Stanford was a precursor.
  3. Layer 1 is the programming model (launched in 2006). The CUDA language is derived from C++. It shows GPU threads and memory to the programmer. You write kernels in it. Kernels compile to PTX.
  4. The NVIDIA driver is the bridge from CPU to GPU. It allocates memory, copies data and launches kernels. The article shows a vector-addition kernel with 256 threads in each block.
  5. This level is low and easy to get wrong. Crashes are hard to diagnose. Some details, for example the warp size, only apply to NVIDIA. AlexNet (2012) used custom kernels of this type.
  6. Layer 2 is the libraries. Raw CUDA is hard to use and is not performance portable. A kernel for one GPU generation can run far below peak on the next generation.
  7. NVIDIA built closed-source libraries: cuDNN (2014), cuBLAS and cuFFT. NVIDIA pays the cost to rewrite them for each generation. cuDNN let TensorFlow (2015) and PyTorch (2016) scale.
  8. Layer 3 is complete solutions for AI engineers who do not write GPU code: Triton Serving, TensorRT and TensorRT-LLM.
  9. Together, these layers form a brand and an ecosystem, as the Java ecosystem or an operating system does. The four traits: a huge code base, many tools and libraries, tuning for each new architecture, and closed internals.
  10. Lattner concludes that CUDA won through strategy, ecosystem and momentum more than through raw performance.
CAUTION

The word “Triton” has two meanings in the series. In Part 2, “Triton Serving” is an NVIDIA product that serves models. In Part 7, “Triton” is the OpenAI language for GPU kernels. They are different things.

READING R1-P3Part 3 · How did CUDA succeed?—

Week 0Chris Lattner · 12 February 2025 · Original article

1. Main idea

CUDA won through long-term strategy as much as through quality. NVIDIA kept one compatible GPU line, built the libraries that AI frameworks needed, and arrived at the right time. These forces now reinforce each other. Lattner says they also begin to limit progress.

2. Key points

  1. Alternatives exist: ROCm from AMD, oneAPI from Intel and SYCL frameworks. None has displaced CUDA. Lattner gives these causes: execution, investment, continuity, lock-in and some luck.
  2. Early growth. A new platform needs developers, and developers avoid niche hardware. NVIDIA kept its GPUs compatible across generations. Jensen Huang explains this on the Acquired podcast.
  3. Developers learned CUDA on cheap gaming GPUs and later moved to expensive datacenter GPUs. NVIDIA made one contiguous line. It accepted some inefficiency for one ecosystem. Lattner compares this to the iPhone line of Apple.
  4. The AI wave. AlexNet (2012) trained on two GeForce GTX 580 GPUs. Then TensorFlow (2015) and PyTorch (2016) arrived. NVIDIA invested in cuDNN and TensorRT so that these frameworks ran best on NVIDIA GPUs.
  5. Framework teams did not have to tune at a low level. NVIDIA did it for them. Each new hardware generation came with a new CUDA version. This tied the frameworks to NVIDIA hardware.
  6. Why did Google and Meta allow this? They used AI for products and research. They also built their own chips, the TPU and an in-house accelerator, so they focused on those.
  7. Rivals faced a hard task. They had to copy the libraries and also chase each new NVIDIA advance. Efforts such as XLA and PyTorch 2 came partly from this struggle.
  8. The GenAI surge. ChatGPT launched in late 2022. Companies spent billions on infrastructure, and much of it went to NVIDIA. Training and serving are costly, so small efficiency gains save large sums.
  9. Companies had to optimize for CUDA or fall behind. FlashAttention-3 was built only for Hopper GPUs. DeepSeek wrote PTX directly. Lattner expects another round of rewrites for Blackwell.
  10. The cycle has four steps. GenAI creates demand. NVIDIA controls the supply. The largest install base attracts the most research, and this research justifies more investment.
  11. Lattner ends with a warning. The same forces that protect CUDA also limit technical progress. He asks if CUDA is good for developers or only for NVIDIA.

READING R1-P4Part 4 · CUDA is the incumbent, but is it any good?—

Week 0Chris Lattner · 20 February 2025 · Original article

1. Main idea

The answer depends on the person who asks. CUDA is essential but painful for AI engineers and for performance engineers. It is a barrier for people who want portable software. It also slows NVIDIA itself.

2. Key points

  1. AI engineers. They gain from the maturity of CUDA and from the many libraries built for it first. Their main pain is version management. The toolkit, the driver and the framework must match.
  2. Lattner gives an example of a mismatch between CUDA 11.7 and CUDA 12.1. He also mentions driver problems after an upgrade. NVIDIA answers with point solutions such as NIM, which raise lock-in.
  3. Performance engineers. CUDA dates from 2007, before deep learning. It does not show all that modern GPUs can do, for example Tensor Cores and sparsity.
  4. FlashAttention-3 and DeepSeek go below CUDA to PTX. PTX is only in part documented. It changes between generations and is hard to use.
  5. Tensor Cores give most of the FLOPs of a model, but they are hard to program. Programmers use trial and error. The libraries cuBLAS and CUTLASS help. The documents lag behind each new GPU.
  6. AI work is in Python, but CUDA is C++. The change of language slows work. C++ templates cause slow compiles and error messages that are hard to read.
  7. Portable software. CUDA runs only on NVIDIA hardware. Early OpenCL back ends in TensorFlow and PyTorch lagged behind in speed and features. Developers target CUDA first, which makes CUDA stronger.
  8. NVIDIA itself. The CUDA moat gave NVIDIA about 98 percent of the datacenter GPU market by 2023. Jim Keller disagrees and says CUDA is a swamp, not a moat. He compares it to x86 and Intel.
  9. Jensen Huang says NVIDIA has more software engineers than hardware engineers. Usability problems force NVIDIA to hire many people. The size of the stack also slows new hardware launches.
  10. Backward compatibility has become technical debt. This is the innovator’s dilemma. Blackwell broke compatibility with some Hopper PTX operations. Code written at the PTX level can need a rewrite.

READING R1-P5Part 5 · What about OpenCL and CUDA C++ alternatives?—

Before the sessionsChris Lattner · 5 March 2025 · Original article

1. Main idea

C++-based portable GPU models (OpenCL, SYCL, oneAPI) did not become important for AI. Lattner gives these causes: competitors who must also cooperate, slow committees, fragmentation and the strategy of NVIDIA. He ends with seven requirements for a successful unifier.

2. Key points

  1. OpenCL was a C++-like way to write GPU code. In 2008, Lattner was a lead engineer on it at Apple. It was the first production use of the Clang compiler. Apple gave it to the Khronos Group.
  2. OpenCL was widely used in mobile and embedded devices. It still runs on Android and on DSPs. It inspired SYCL, Vulkan, SPIR-V, oneAPI and WebCL. But it did not become the platform for AI.
  3. “Coopetition at committee speed”. Hardware vendors cooperate on a standard and compete on hardware. They keep new features until their products ship. Then they add vendor extensions.
  4. Apple wanted speed and secrecy. It left OpenCL for Metal. It never brought OpenCL to iOS and later deprecated it on macOS.
  5. Technical problems. Apple gave a specification, not a full shared implementation. Each vendor made its own fork. Conformance tests were weak. Portability suffered.
  6. AI needed more. TensorFlow and PyTorch needed high-level libraries for matrix multiplication, FlashAttention and scale. OpenCL had no standard support for Tensor Cores.
  7. Lattner says OpenCL can be 5 to 10 times slower than CUDA or vendor-native code. For GenAI, where compute is costly, this is a deal-breaker.
  8. NVIDIA worked with the frameworks on its own libraries. It kept a limited OpenCL implementation, with no Tensor Core access. CUDA stayed the main path.
  9. Lattner is also doubtful about oneAPI, now the UXL Foundation. It is open in name, but one hardware vendor controls it.
  10. The article ends with a link to AI compilers. Hand-written code cannot keep pace with the number of chips and workloads. This led compiler engineers, including Lattner, into AI.
The seven requirements for a successful unifier
  1. A reference implementation, not only a specification and tests.
  2. Strong leadership and vision from the owner of that implementation.
  3. Top performance on the hardware of the industry leader.
  4. Fast evolution, to keep pace with AI research and hardware.
  5. Developer appeal: usability, tools and fast compile times. “C++ like” does not help in AI.
  6. An open community, because adoption decides success.
  7. No fragmentation into incompatible forks.

READING R1-P6Part 6 · What about TVM, XLA, and AI compilers?—

Before the sessionsChris Lattner · 12 March 2025 · Original article

1. Main idea

AI compilers answer one problem: nobody can hand-write GPU kernels for every operator and every chip. TVM and XLA were the first main attempts. They did not reach their goal. The causes were performance, fragmentation, incentives and the arrival of GenAI.

2. Key points

  1. At first, engineers wrote CUDA kernels by hand. NVIDIA packed common kernels in libraries such as cuDNN. Then models grew, and the number of operators in the frameworks grew to thousands.
  2. An AI compiler takes high-level operations from a framework and makes efficient GPU code. Its main technique is kernel fusion. See Figure 2.
  3. The example is a matrix multiplication followed by a ReLU. Without fusion, the product goes to global memory and then back for the ReLU. Memory traffic dominates the run time.
  4. With fusion, the ReLU runs inside the multiplication loop. The intermediate result stays on the chip. Lattner reports gains of up to about 2 times, which depend on hardware and size.
  5. The problem grows fast. Hundreds of operations combine with hundreds of others. New data types, for example float8, add more cases. More types of hardware add more again. Fixed libraries cannot keep up.
  6. TVM (Tensor Virtual Machine). It began in about 2016 at the University of Washington, with Tianqi Chen and Luis Ceze. It became an Apache project. ARM, Qualcomm, Facebook and Intel contributed.
  7. Three lessons from TVM. It was late to support Tensor Cores. Vendors made forks, which caused fragmentation. It was built for simple “TradAI” operators, so it fell behind on GenAI, and auto-tuning made compiles slow.
  8. NVIDIA bought OctoAI in late 2024. The core developers of TVM founded OctoAI. Thus the future of TVM is not clear.

READING R1-P7Part 7 · What about Triton and Python eDSLs?—

Before the sessionsChris Lattner · 26 March 2025 · Original article

1. Main idea

Python eDSLs try to give CUDA-level control with the ease of Python. They have costs in performance, portability, tools and governance. Triton is the best-known example. It is useful, but it does not challenge CUDA. Lattner expects more fragmentation.

2. Key points

  1. The tension: compilers hide the hardware to be easy to use. GenAI needs hardware control for speed. CUDA C++ gives control, but AI work is in Python, and Python does not run on a GPU.
  2. An embedded domain-specific language (eDSL) reuses the syntax of a host language, here Python. It changes how the code runs. PySpark, tf.function and torch.fx are examples.
  3. Most eDSLs use a Python decorator. In Triton, @triton.jit intercepts the function. Triton parses it to an abstract syntax tree (AST), analyzes it and makes GPU code.
  4. The advantages. The authors do not need a new language, parser or toolchain. Users keep their IDE, debugger, pip and conda.
  5. Challenge 1: the code looks like Python, but it is not Python. In a Numba example, a generator expression and the built-in sum fail. The failures can be silent or hard to understand.
  6. Challenge 2: errors and tools. Users get compiler stack traces. Python debuggers often fail. The code cannot use all Python libraries.
  7. Challenge 3: limited expressiveness. An eDSL cannot add new keywords or constructs, as CUDA C++ can.
  8. Triton began as research by Philippe Tillet at Harvard (published in 2019). It grew when he joined OpenAI and when PyTorch 2 adopted it.
  9. Triton’s model is block-centric. You program blocks, not single threads. Functions such as tl.program_id, tl.arange, masked tl.load and tl.dot do the work. tl.dot reaches the Tensor Cores.
  10. Triton also automates vectorization. It makes double buffering and software pipelining easier for non-experts.
  11. Where Triton falls short. Speed: about 20 percent behind CUDA on the H100. Lattner says this can mean a $1B cloud bill instead of $800M at scale.
  12. Governance: OpenAI owns the roadmap. Tools: no Nsight Compute support. Portability: A100 kernels often run badly on the H100. AMD support lags. TPUs, Groq and Cerebras do not fit the SIMT model.
  13. Other eDSLs. Pallas (JAX, mainly TPU). CUTLASS Python (announced at GTC 2025, for Blackwell first). cuTile (a tile-based NVIDIA eDSL; NVIDIA reportedly said it is about 15 percent slower than TRT-LLM).
  14. Lattner sees many tools as fragmentation. He ends with MLIR, which enabled Triton and cuTile. He says MLIR has the same governance problems. Part 8 covers it.

READING R2The Architecture of Open Source Applications · “LLVM”—

Week 0Chris Lattner · The Architecture of Open Source Applications, Volume 1 (2011) · Original article

1. Main idea

This chapter explains why LLVM is built as a set of reusable libraries around one well-defined IR. The three-phase compiler design, the modular pass pipeline and the declarative target descriptions come from this idea. MLIR and Mojo use the same principles.

2. Key points

  1. Introduction. LLVM began in December 2000. It is an umbrella project of low-level tools. Its special feature is its architecture. Before LLVM, language implementations were monolithic. Parsers were hard to reuse, and static and runtime languages shared little code.
  2. Classic compiler design. The front end parses and checks the source and builds an AST. The optimizer makes the code faster and does not depend on the language or target. The back end maps the code to a target instruction set.
  3. Typical back-end tasks are instruction selection, register allocation and instruction scheduling. Interpreters and JIT compilers follow the same model. The JVM uses bytecode as the border between front end and optimizer.
  4. Implications. With a shared optimizer, a new language needs only a new front end, and a new target needs only a new back end. You build N + M parts, not N × M compilers. A shared compiler also attracts a large community.
  5. Earlier systems. The Java and .NET virtual machines share a JIT and a runtime, but they force a garbage collector and an object model. Translation to C is easy, but it hurts exceptions, debugging and compile speed.
  6. GCC has many front ends and back ends. But it grew from a C compiler with languages added on top. It is hard to embed or to use as a JIT. Global state, weak invariants and layering violations are the causes.
  7. LLVM IR. It is a low-level, RISC-like virtual instruction set. It has simple instructions in three-address form, labels and basic blocks, a simple static type system, and call and return. It has an unlimited number of named temporaries that start with %.
  8. IR has three equal forms: text (.ll), an in-memory data structure, and compact bitcode (.bc). The tools llvm-as and llvm-dis convert between text and bitcode.
  9. The chapter shows two small functions. add1 adds two integers with one instruction. add2 uses a compare, a branch and a recursive call. Its C form is a recursive function that adds in an inefficient way.
  10. Writing an optimization. Most optimizations do three steps: match a pattern, check that the change is safe, and change the code. The example is arithmetic identities, such as X − X = 0 and X − 0 = X. These do not always hold for IEEE floating point.
  11. LLVM gives a simplification interface with a helper for each opcode. A template-based matching library, with names that start with m_, describes patterns. replaceAllUsesWith then swaps the old value for the simpler one.
  12. IR as the only interface. A front-end author must only know the IR. Because IR has a text form, a front end can write text and pipe it through any optimizer and code generator. GCC did not have this property.
  13. A collection of libraries. The optimizer is a pipeline of passes. Each pass is a separate analysis or change. The PassManager schedules them and resolves their needs. At -O0 Clang runs none, and at -O3 it ran 67 passes in LLVM 2.8.
  14. A client can choose and order passes. A JIT for image processing can skip the inliner and alias analysis. The linker includes only the passes that the client uses, because each pass is in an archive library.
  15. Code generator. It is also a set of passes: instruction selection, register allocation, scheduling, code layout and assembly output. A target can change or add passes. The x86 target reduces register pressure. The PowerPC target uses a latency-based scheduler.
  16. TableGen. Target facts are in declarative .td files that the tblgen tool processes. A register class such as GR32 and an instruction such as NOT32r are the examples. One description drives selection, allocation, encoding, parsing and printing, and it can make an assembler and a disassembler.
  17. Choose when each phase runs. Bitcode can be saved. Link-time optimization (LTO) optimizes the whole program when the linker joins the files. Install-time optimization makes machine code on the user’s device.
  18. Unit tests. LLVM tests load textual IR, run one pass and check the output with FileCheck. This is better than a test that compiles a whole C file. BugPoint automatically reduces a failing input to a small one.
  19. Retrospective. Modularity is a defense against mistakes, because you can replace a part. LLVM accepts API-breaking changes and keeps old .ll and .bc files readable. Lattner gives LLDB as an example of reuse. He warns that LLVM can calcify with age.
WHAT HAS CHANGED SINCE 2011

The ideas are still correct. Some details are not the same in LLVM 18, which you installed in Week 0.

  • Pointers. The chapter writes typed pointers, for example i32**. Current IR uses one opaque pointer type, ptr.
  • Pass manager. The FunctionPass and runOnFunction style is the old pass manager. The new pass manager is the default. This is why Week 1 uses opt -passes=....
  • Constant propagation. The old constprop pass is gone. The instsimplify and instcombine passes fold constants now.
  • Test reduction. LLVM now has llvm-reduce, which the documents recommend for most cases. BugPoint still exists.
  • TableGen. It is still in use. MLIR uses it to define operations (ODS) in Weeks 5 and 6.

6. Self-test

Q1Why do N front ends and M back ends need only N + M parts?
The optimizer works on one shared IR. Each front end makes that IR, and each back end reads it. There is no need for each pair.
Q2Name the three forms of LLVM IR.
Text (.ll), an in-memory data structure and binary bitcode (.bc).
Q3What is link-time optimization?
The compiler saves bitcode in the object files. The linker joins them and then optimizes the whole program, so it can inline across files.
Q4Why is a textual IR good for testing?
A test loads IR, runs one pass and checks the result. The test does not depend on the front end or on other passes.
